# Vibe & AI Detector — MVP Plan

Build a single-page web app that accepts a GitHub repo URL or a public website URL, runs heuristic analysis, and returns two scores (Vibe Score, AI Score) with an evidence list.

## User flow

1. User pastes a URL into an input on `/`.
2. Backend detects input type (GitHub repo vs. website) and runs the matching analyzer.
3. Results page renders two score gauges (0–100) + categorized evidence rows (signal, weight, snippet/link).

## Routes

- `/` — landing + URL input form, submits to results.
- `/scan/$id` — results page (score gauges + evidence table). Results held in-memory per request for MVP (no DB); re-submit re-scans.

## Server functions (TanStack `createServerFn`)

- `analyzeUrl({ url })` — dispatches to `analyzeGithub` or `analyzeWebsite`.
- `analyzeGithub({ owner, repo })` — uses GitHub connector via gateway:
  - `GET /repos/{o}/{r}` (metadata)
  - `GET /repos/{o}/{r}/contents/` (root tree) + selectively fetch `package.json`, `tailwind.config.*`, `.cursorrules`, `copilot-instructions.md`, `AGENTS.md`, top CSS files
  - `GET /repos/{o}/{r}/commits?per_page=100` (commit messages, authors, sizes via stats)
  - Run signal extractors on fetched blobs.
- `analyzeWebsite({ url })` — server-side `fetch` of HTML; parse for Tailwind class patterns, CSS `--var` usage, `<link>` stylesheets (fetch top 2), framework hints in `<script src>`.

## Signal extractors (pure functions, in `src/lib/detectors/`)

Vibe signals:
- `tailwind.config.*` present → +30
- Tailwind utility class density in HTML/JSX/CSS (regex: `\b(bg|text|p|m|flex|grid|rounded|border)-\S+`) → up to +25
- shadcn/ui, @radix-ui/*, tailwindcss, class-variance-authority, lucide-react in `package.json` → +20 combined
- CSS custom-property density (`--color-`, `--radius-`, `:root { --... }`) → +15
- Default font "Inter" + default shadcn tokens → +10

AI signals:
- Presence of `.cursorrules`, `.windsurfrules`, `copilot-instructions.md`, `AGENTS.md`, `CLAUDE.md` → +30 each (capped)
- Commit messages matching `/copilot|cursor|claude|chatgpt|generated by ai|lovable/i` → +25
- Committer/author name matching bot patterns (`*[bot]`, `copilot`) → +20
- Large initial commit (>1000 additions in first commit) → +15
- README / comment "tutorial voice" regex (`\b(we will now|in this example|let's|first,|step \d+:)\b`, numbered list density) → up to +15
- Emoji-heavy README section headers (common LLM output) → +5

Each signal returns `{ id, category: 'vibe'|'ai', weight, evidence: string, sourceRef?: string }`. Final score = clamp(sum, 0, 100).

## GitHub connector

Use `standard_connectors--connect` with `connector_id: 'github'`. All GitHub calls go through the gateway (`https://connector-gateway.lovable.dev/github/...`) from server functions using `LOVABLE_API_KEY` + `GITHUB_API_KEY` from `process.env`.

## UI

- Minimal, no shadcn kit needed for MVP; use plain Tailwind + one card component.
- Landing: hero + URL input + submit button + tiny "what this detects" blurb.
- Results: two large circular score gauges (SVG), verdict label (Low/Med/High), collapsible evidence list grouped by category with weight badges and snippet previews.
- Loading state on submit (server function is synchronous; typical scan 3–8s).

## Out of scope for MVP

- Persistence / scan history (no DB).
- ML classifier (heuristics only; hooks left in scoring module for later).
- Dynamic headless-browser rendering (fetch static HTML only).
- Private repo auth beyond what the connector provides.
- CI/GitHub Action packaging.

## Technical notes

- Website fetch: 10s timeout, 2MB cap per resource, fetch HTML + up to 2 linked stylesheets.
- GitHub fetch: cap at ~15 file reads per scan to stay within rate limits; skip binary files.
- All regex/AST work in plain TS — no tree-sitter for MVP (regex is enough for these signals).
- Errors (private repo, 404, fetch fail) return a typed `{ error }` shape rendered as a friendly message.

## Deliverables in first build pass

1. GitHub connector linked.
2. `src/lib/detectors/` with signal modules + scoring aggregator.
3. `analyzeGithub` + `analyzeWebsite` server functions.
4. `/` input page and `/scan/$id` results page (using URL query param or in-memory cache keyed by hash of URL).
5. Head metadata on both routes.
